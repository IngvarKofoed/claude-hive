# Ship lane: Land on main squashes, tests and pushes in one go

The last lane. A card you accepted in Try it waits in Ship with **Land on main**, and pressing it is your approval.
The hive then does everything in one go:
- it squashes the card's branch onto the latest main as one commit;
- it runs the project's tests on that commit;
- it puts the commit on main: a push to `origin` if the project has one, or your local main if it doesn't;
- it brings your checkout's main up to date when that's safe;
- it removes the card's worktree and branch, and moves the card to Done.

A conflict with main sends the card back to Build, and after Check it comes straight back to Ship. A failing test
stops the landing and offers Retry or Back to Build. Nothing ever goes through your uncommitted work.

## Outcome

**What you get:**

- **One button lands the card:** Ship shows what will happen and **Land on main**. Pressing it squashes, tests,
  pushes and cleans up, with each step as a line in Ship's history. The card ends in Done, which shows the commit it
  landed as.
- **Clean history:** one commit per card on main, in the repo's own commit style, ending with the spec's path and a
  `Hive-Card:` trailer. There are no merge commits, and no branch is left behind.
- **Your checkout is safe:** main is pushed without going through it. Its own main moves only when that's safe, and
  otherwise the Done page says it's behind.
- **Problems stop it, never half-land it:**
  - a conflict with main sends the card back to Build, and after Check it returns to Ship;
  - a failing test keeps the card in Ship with Retry and Back to Build;
  - main moving meanwhile means the hive squashes and tests again.

**How to verify:**

- **Land a card:** in a project with an `origin`, press Land on main on a card in Ship. `origin/main` gains one commit
  in the repo's style, ending with `Spec:` and `Hive-Card:` lines. The worktree and `hive/<card>` are gone, and the card is in Done,
  showing the commit.
- **Your dirty checkout:** with uncommitted changes in your checkout and main checked out there, land a card. Your
  files are untouched, and Done says your checkout's main is behind `origin`.
- **Unpushed commits:** with a local commit on main that isn't on `origin`, Land on main is refused with "Push them
  first".
- **No remote:** in a scratch repo without `origin`, landing moves local main when main isn't checked out, or when
  your checkout is clean. With uncommitted changes, it waits and says why.
- **A conflict:** push a change to `origin/main` that clashes with the card, then press Land on main. The card goes to
  Build. The developer resolves the merge, Check passes, and the card is back in Ship.
- **A failing test:** with a test that fails on the squash, the card stays in Ship with the output, Retry and Back to
  Build.

## Key decisions

- **Pressing Land on main is the approval, and the rest runs without stopping** (diverges from `CONCEPT.md`, Ship:
  "Approve" after the squash and the checks). You chose approving first over seeing the prepared commit first: one
  action, and anything that goes wrong stops the landing before main changes.
- **With an `origin`, the whole hive works from a freshly fetched `origin/main`** (new; changes worktree creation and
  Build's merge from `2026-11-26-build-lane-developer`).
  - **Worktrees** branch from it when a card enters Refine. **Build** merges it at each entry, after a fetch, and the
    merge note names it ("Brought in origin/main: 2 new commits."). **Ship** squashes onto it.
  - So a conflict Ship finds is the same one Build's merge shows the developer, and the loop Ship → Build → Ship can't
    come back with nothing to resolve.
  - **Ship refuses while your local main has commits `origin/main` lacks:** "Your local main has 3 commits that aren't
    on origin. Push them first, then press Land on main." They'd otherwise be folded into the card's commit and pushed
    under its message.
  - **A fetch that fails** (offline) falls back to the last fetched `origin/main`, with a note. Without an `origin`,
    local `main` is the base everywhere, as now.
- **The squash is made without touching any working files** (new; reuses `ship-squash-then-push`'s "squash onto the
  latest main").
  1. **Fetch:** `git fetch origin main` in your checkout, if there's an `origin`. The base is then `origin/main`, or
     your local `main` without a remote.
  2. **Squash:** `git merge-tree --write-tree <base> hive/<card>` gives the merged tree, or the conflicting files.
  3. **Commit:** `git commit-tree <tree> -p <base>` makes the one commit.

  A conflict is found before anything changes, so there's no half-done merge to abort.
- **The tests run on the squash itself** (extends the worktree setup's `test` command, which replaces
  `Project.testCommand`).
  - The card's worktree is switched to the squash commit, detached, and the setup's test command runs there, with a
    10-minute limit.
  - No test command, or no finished setup: a note says the squash wasn't tested, and the landing goes on.
  - A failing test switches the worktree back to `hive/<card>` and stops.
- **Main is moved forward only, never forced** (reuses `ship-squash-then-push`).
  - **With `origin`:** the hive runs `git push origin <commit>:refs/heads/main`.
    - **Main moved:** the push is refused as not a fast-forward, so the hive fetches, squashes and tests again, up to
      3 times.
    - **Anything else:** a fetch or push that fails for another reason (offline, auth, a protected branch, a server
      hook), and the third refusal, stop the landing. The worktree goes back to `hive/<card>`, `Card.landing` is
      cleared, and an error line shows git's output with Retry.
    - **Your `pre-push` hook** runs, as for any push to main, and a rejection by it stops the landing the same way.
  - **Your local main:**
    - If main isn't checked out anywhere, it moves by compare-and-swap (`git update-ref`), and only as a
      fast-forward.
    - If main is checked out in a clean checkout, it moves with `git merge --ff-only` there.
    - Otherwise it's left alone. With `origin`, Done says it's behind. Without `origin`, the landing waits:
      "Commit or stash your changes, then press Land on main again."
- **A conflict goes back to Build and returns to Ship** (reuses `ship-squash-then-push`; extends the Try it feedback
  path).
  - The card goes to Build with your feedback field set to "Landing on main stopped on conflicts in …", and a new
    `Card.shipAfterCheck`.
  - Build's usual merge of main surfaces the conflict for the developer to resolve.
  - A passing Check round then moves the card to Ship instead of Try it.
  - A failing test's Back to Build works the same way, with the test output as the text.
- **A short session writes the commit message in the repo's style** (reuses `CONCEPT.md`, Ship: "in the repo's commit
  style"; new role `roles/committer.md`, Sonnet, one-off and not kept).
  - It gets the card's title, the spec's path and its Outcome, the last 15 commit messages on main for the style, and
    the squash's `git diff --stat`. It returns `{ subject, body }` as a fixed-format report.
  - The hive appends `Spec: <path>` and `Hive-Card: <card id>` itself, so the trailer never depends on the session.
  - A session that fails, returns no report, or runs past 3 minutes falls back to a message from the card: the
    title, the first "What you get" bullet, then the trailers. A note says so.
  - The message is written once per landing. A squash again after main moved reuses it.
- **A landing survives a hive restart** (new: `Card.landing`). The hive stores the base and the squash commit before
  the push, and whether the push went through. At startup:
  - a landing whose commit is on main (checked with `merge-base --is-ancestor` after a fetch) is finished: your
    checkout's main, the clean-up, Done;
  - any other landing is undone: the worktree goes back to `hive/<card>`, and Ship says "Landing was cut off. Nothing
    reached main." with Retry;
  - if the startup fetch fails, the landing is left as it is, and Ship says "Landing was cut off, and the hive couldn't
    reach origin to see how far it got." with Retry. It makes no claim about main.

  A squash whose tree is the same as the base's is never committed: the card's changes are already on main, so the
  landing goes straight to the clean-up, with a note saying so.

## Goals

- **Cards reach main:** the hive's loop closes, from an idea to a commit on main.
- **Main and your checkout are never put at risk:** no forced push, no merge commit, and no change to uncommitted
  work.

## Non-goals

- **Reviewing the prepared commit before landing:** you chose approving first.
- **Saving each lane's diffs into the card's history before squashing,** history tabs, the archive at Done, and search
  by the `Hive-Card:` trailer.
- **Keeping the card's checkpoint commits:** deleting `hive/<card>` makes them unreachable, so cards landed before the
  history slice will never have per-lane history. This is a known, permanent gap you accepted. Rejected parking the
  branch under `refs/hive/landed/<card>`.
- **A rule that turns approval off,** since rulebooks don't exist.
- **Branches other than `main`, remotes other than `origin`,** and a pull request instead of a push.
- **Running the project's commit hooks:** `commit-tree` runs none, and the tests are the check. A `pre-push` hook does
  run, since the push is a real push to main.

## Design

### Moves

All in `board/moves.ts`, each with a test.

| From | Event | To |
| --- | --- | --- |
| Try it | You accept | Ship, as before |
| Ship | You press **Back to Try it**, before landing starts | Try it, as before |
| Ship | The landing succeeds | Done |
| Ship | The squash conflicts with main | Build, with `shipAfterCheck` and the conflicting files as the developer's text |
| Ship | A test fails, and you press **Back to Build** | Build, the same way, with the test output |
| Check | A round passes while `shipAfterCheck` is set | Ship, not Try it; the flag is cleared |
| any | The card moves to Try it or Spec, or Try it's Send to Build | As before, and `shipAfterCheck` is cleared |

### Landing, step by step

`land(cardId)` runs these steps one card at a time per project. While one runs, another card's Land on main is
refused. Each step adds a line to Ship's history.

1. **Refuse** if another card of the project is landing, if the card isn't in Ship, if something runs, if the card's
   worktree has uncommitted changes and you didn't choose to discard them, or if your local main has commits
   `origin/main` lacks. Without
   `origin`, also refuse at once when local main can't move (checked out in a checkout with uncommitted changes),
   with the waiting line, rather than after the tests.
2. **Fetch and merge** as in Key decisions (`merge-tree`). On a conflict: move to Build, as above.
3. **Write the message:** run the committer session, or fall back to the template.
4. **Commit and store:** run `commit-tree` with that message, and store `Card.landing` `{ base, commit, pushed: false }`.
5. **Test:**
   - Switch the worktree to the commit, detached, then run the test command. The worktree is clean by then (step 1),
     so nothing is discarded, and the tests run on exactly what lands.
   - On a failure, which includes running past the 10-minute limit: switch back to `hive/<card>`, clear
     `Card.landing`, and add an error line with the last 30 output lines and the actions `retry` and `back-to-build`.
6. **Push or move main** as in Key decisions.
   - A refused push loops back to step 2, at most 3 times, keeping the message.
   - Without `origin`, a checkout that got uncommitted changes since step 1 stops here: the worktree goes back to
     `hive/<card>`, `Card.landing` is cleared, and the waiting line offers Retry.

Every Retry starts the landing over from step 1, message included.

A card that comes back to Ship from Build and Check waits for you to press Land on main again: its code changed since
you approved.
7. **Mark it:** set `Card.landing.pushed = true`.
8. **Update your local main** when it's safe, as in Key decisions. Store whether it happened, and why not.
9. **Clean up:**
   - stop the card's app and anything on its ports;
   - `git worktree remove --force` and `git branch -D hive/<card>`;
   - free the card's ports;
   - set `Card.landed` `{ commit, subject, base, remote, checkout }`, clear `Card.landing`, and move to Done.

   A failed clean-up is a note, and the card still goes to Done.

**Uncommitted work in the card's worktree** isn't on the card's branch, so it can't land. It's often left from trying
the app. While there is any (tracked changes, or untracked files that aren't git-ignored), Land on main is refused.
The Ship page lists it from `git status --porcelain`, and offers two ways on:
- **Discard them and land:** `git reset`, `git checkout -- .` and `git clean -fd` in the worktree, which drop staged
  and unstaged changes alike and leave git-ignored files such as `.env` alone, then the landing;
- **Back to Try it.**

### The page

- **Ship:**
  - A panel lists the steps Land on main will take, the base it will land on (`origin/main` or `main`), and any
    uncommitted work that won't land.
  - With no finished setup or no test command, it says "No tests will run" and why, before you press.
  - It has **Land on main** (disabled while there's uncommitted work), **Discard them and land** (only then), and
    **Back to Try it**.
  - Ship's history is shown read-only, with its error lines' Retry and Back to Build.
  - On the right, as in Try it: Check, Build and the plan.
- **Done:**
  - "Landed on main as `<short commit>`: <subject>", and whether it was pushed to `origin`.
  - Your checkout's main: "up to date", or why not.
  - The Spec, Check, Build and plan panels as a read-only record.
- Ship and Done become `implemented: true`.

### Data and API

- **Shared types:**
  - `Landing { base, commit, pushed }` and `Landed { commit, subject, base, remote: boolean, checkout: string }`,
    where `checkout` is "updated" or the reason it wasn't;
  - `CardDetail.landed: Landed | null`, `CardDetail.landing: boolean`, `CardDetail.uncommitted: string[]` (for Ship);
  - the actions `retry` and `back-to-build` reused on Ship's error lines.
- **Database:** the `cards` columns `landing`, `landed` (JSON) and `ship_after_check`.
- **Role:** `roles/committer.md` and its `COMMIT_SCHEMA` (`subject`, `body`).
- **API:** `POST /api/cards/:id/land`, with `{ discard: true }` for Discard them and land. Retry on a Ship error line calls the same. `POST /api/cards/:id/back-to-build`
  extends to Ship.
- **Git service:**
  - `squashOnto(root, worktree, branch)` returns the commit, or the conflicting files;
  - `pushMain(root, commit)`;
  - `moveLocalMain(root, commit, base)`;
  - `removeCardWorktree(root, worktree, branch)`;
  - `createCardWorktree` and `mergeMain` gain the fetched `origin/main` base when there's an `origin`.

  Each is tested on a throwaway repo with a bare repo as its `origin`.

### Docs that change

- **`CONCEPT.md`, Ship:**
  - step 3: the approval is pressing Land on main;
  - drop "Ship saves each lane's changes" as not built yet.
- **`ARCHITECTURE.md`:**
  - **Git:** the Ship row: `merge-tree` and `commit-tree`, tests on the squash in the worktree, push or fast-forward
    without force, and up to 3 retries. The "Card enters Refine" and "Build starts" rows use the fetched `origin/main`
    when there's an `origin`.
  - **Card Moves:** the rows above, and the end of "until Ship is built".
  - **Data model:** `landing`, `landed`, `shipAfterCheck`, and `Project.testCommand` gone.
  - **API:** `land`.
  - **Restarts:** "Ship can start over" becomes the startup check above.

## Alternatives considered

- **Prepare first, then approve** (the docs' order): you'd see the exact commit and the test result before landing.
  You chose one button.
- **Squashing with `git merge --squash` in the worktree:** a conflict would leave a half-done merge to abort.
  `merge-tree` finds it without touching any file.
- **Running the project's commit hooks:** `commit-tree` doesn't, and a hook that fails at landing would be a fourth way
  to stop. The tests on the squash are the check.
- **A message from the card only:** plain code, with nothing to wait for. It stays as the fallback, but your repos
  have their own commit styles, and the docs ask for the repo's style.
- **Sending the card straight back to Build when a test fails:** a flaky test would send it through Build and Check.
  It stays in Ship with Retry and Back to Build.
- **Committing uncommitted worktree work before landing:** it's usually what was left from trying the app, and
  committing it would land files nobody reviewed.
- **Stashing leftovers and restoring them if the landing fails:** more state to put back on every failure. Refusing,
  with a deliberate Discard, keeps the tests on exactly what lands.
- **One base per lane** (local main for worktrees and Build, `origin/main` for Ship): a conflict at Ship could bounce
  between Build and Ship with nothing to resolve, and unpushed local commits would land under the card's message.

## Implementation strategy

*Not part of the design — a starting point for whoever builds this.*

- **Multi-agent: an Opus lead plus a Sonnet page chunk.**
- **The lead (Opus 5.5)** builds the git service's four functions and the `origin/main` base, with tests against a
  bare `origin`, then the committer role and the hive's `land`:
  - the per-project lock;
  - the steps and their history lines;
  - the conflict and test paths, and `shipAfterCheck`;
  - the startup check;
  - the docs.
- **The subagent (Sonnet 5.5)** builds the Ship and Done pages against the finished types.
